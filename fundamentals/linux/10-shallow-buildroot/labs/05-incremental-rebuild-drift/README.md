# Lab 6.5 — Incremental Rebuild and Drift Diagnosis

**Time:** ~45 min. **Prerequisite:** Lab 6.4.

---

## 1. Buildroot is a state machine, not a dependency graph

This is the fact that costs people days. From `docs/manual/rebuilding-packages.adoc`
(Buildroot 2026.05.2):

> Buildroot does not attempt to detect what parts of the system should be
> rebuilt when the system configuration is changed through `make menuconfig`,
> `make xconfig` or one of the other configuration tools.

and, decisively for this lab:

> once a package has been built, it is never rebuilt unless explicitly told to
> do so.

The same chapter draws the boundary that matters here:

> When a change to the root filesystem skeleton is made, a full rebuild is
> needed. However, when changes to the root filesystem overlay, a post-build
> script or a post-image script are made, there is no need for a full rebuild: a
> simple `make` invocation will take the changes into account.

So there are two classes of change with two completely different propagation
behaviours. Confusing them is the mechanism behind fault F12.

| Change | Propagates on plain `make`? |
|---|---|
| root filesystem overlay content | **yes** |
| post-build / post-image script | **yes** |
| package source (local package) | **no** — the package is already "built" |
| package sub-option | **no** |
| architecture / toolchain configuration | **no** — needs a full rebuild |

## 2. Exercise A — a change that does propagate

```bash
python3 scripts/make_sample_output_tree.py --out build/drift-a --mode healthy
# edit the overlay marker, then re-run the audit
python3 scripts/audit_output_tree.py --output build/drift-a \
    --overlay fixtures/br2-external/board/qemu-virt-a7/rootfs-overlay
```

Because the overlay is applied at the end of the build, a plain `make` picks it
up. Nothing needs to be invalidated.

## 3. Exercise B — a change that does not propagate

The local package `appliance-diag` lives in the external tree. Its source is
compiled by `APPLIANCE_DIAG_BUILD_CMDS` and installed by
`APPLIANCE_DIAG_INSTALL_TARGET_CMDS`. Once
`output/build/appliance-diag-1.0/.stamp_target_installed` exists, a top-level
`make` considers the package complete.

```bash
ls -l --full-time fixtures/output-tree-sample/build/appliance-diag-1.0/.stamp_*
cat  fixtures/output-tree-sample/build/appliance-diag-1.0/.stamp_target_installed
```

Diagnose it from real state, not by assumption:

1. **Symptom** — the source changed, the image did not.
2. **Hypotheses** — at least three, generated by you.
3. **Experiment** — compare the source mtime against the stamp mtimes; run the
   build with the package's own verbose target and observe whether its build
   steps are entered at all.
4. **Evidence** — `make appliance-diag-rebuild all` (or the
   `-reconfigure` variant when the configuration must be re-run) removes the
   package's stamps and re-enters build/install; a plain `make` does not.
5. **Narrow scope** — the source is saved and valid; the image is not corrupt;
   the build simply never re-entered the package.
6. **Root cause** — Buildroot tracks packages by stamp files, at package
   granularity, not by per-file timestamps.
7. **Fix** — the *targeted* rebuild target, not a full tree wipe.
8. **Regression** — the rebuilt image contains the new content, proved by the
   audit and, if you can boot, by the runtime binder.

## 4. Why "delete the whole tree and rebuild" is not the answer

It works. It is also:

* the slowest possible response to a one-package change;
* evidence that you do not know *which* state was stale;
* unavailable in a production pipeline with a shared download cache and a
  time budget.

A full clean rebuild is a legitimate **comparison control** — it confirms that
the source change is real and the package is buildable. It is not a diagnosis.
The diagnosis is: *which stamp made Buildroot skip the work, and which target
removes exactly that stamp.*

## 5. Checkpoint

1. You can list which kinds of change propagate on a plain `make` and which do
   not, and where the manual says so.
2. You can name the stamp file that prevents propagation for a local package,
   and the target that removes it.
3. You can distinguish "the source is wrong" from "the build never re-ran" from
   "the image was not re-packaged".

**Non-proof.** A rebuilt package proves the build re-ran. It does not prove the
new content is in the image, and it does not prove the image boots. Those remain
separate checks — which is exactly why the audit distinguishes
`output/build/`, `output/target/` and `output/images/`.

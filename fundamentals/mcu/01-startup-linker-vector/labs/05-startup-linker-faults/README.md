# Lab 05 — Investigating Startup and Linker Faults

## Objective

Apply a disciplined, hypothesis-driven debugging methodology to diagnose common bare-metal boot and linker failures:
1. Vector address alignment / Thumb bit cleared fault.
2. Linker script `.data` LMA/VMA mismatch fault.
3. Memory region boundary overflow fault.

## Procedure

### Investigation 1: The Missing Thumb Bit Fault
1. Navigate to `faults/fault1_misaligned_vector`.
2. Build the faulty firmware:
   ```bash
   make clean && make
   ```
3. Inspect the vector table and entry point:
   ```bash
   arm-none-eabi-readelf -h build/firmware.elf
   arm-none-eabi-readelf -x .isr_vector build/firmware.elf
   ```
4. Observe that vector 1 contains an even address (bit 0 = 0).
5. Document what the hardware will do upon reset: when the CPU branches to an even PC in Thumb state, it triggers an immediate `UsageFault` (INVSTATE).

### Investigation 2: The LMA-VMA Pointer Corruption Fault
1. Navigate to `faults/fault2_data_lma_mismatch`.
2. Examine the generated map file:
   ```bash
   make clean && make
   grep -A 10 "\.data" build/firmware.map
   ```
3. Check the symbol `_sidata` vs `LOADADDR(.data)`.
4. In this faulty build, `_sidata` was defined as `ADDR(.data)` instead of `LOADADDR(.data)`.
5. Trace what happens at boot: the copy loop attempts to copy from SRAM address `0x20000000` to `0x20000000`, copying uninitialized SRAM garbage over itself instead of loading initial values from Flash!

### Investigation 3: The SRAM Overflow Fault
1. Navigate to `faults/fault3_memory_overflow`.
2. Attempt to build:
   ```bash
   make clean && make
   ```
3. Observe the linker error output generated by the original `ASSERT` commands in the linker script:
   ```text
   Linker Error: SRAM exhausted! BSS and stack exceed 20 KB capacity.
   ```
4. Notice how the assertion protects against silent stack-memory collisions before flashing.

## Expected Observation

- Fault 1: Even address at vector 1 causes hardware fault.
- Fault 2: Compilation succeeds, but `.data` variables evaluate to random noise at runtime.
- Fault 3: Linker stops the build with explicit pedagogical error message.

## Questions

1. Why does Fault 2 compile without any compiler warning? Which tool in the toolchain reveals the error?
2. If a linker script lacks an `ASSERT` for memory limits, does the linker always warn if the image exceeds physical SRAM? (Hint: check how ld treats memory boundaries without MEMORY regions or user assertions).

## Failure Modes

- **HardFault on boot:** Bit 0 of Reset_Handler address in vector table is 0 (even address), triggering `INVSTATE`.
- **Garbage in global variables:** `_sidata` assigned `ADDR(.data)` instead of `LOADADDR(.data)`, copying uninitialized RAM over itself.
- **Linker overflow error:** BSS/data sections exceed physical memory bounds.

## Debug Strategy

When diagnosing an unknown firmware image:
- Step 1: Run `readelf -h` to check entry point parity.
- Step 2: Run `objdump -s -j .isr_vector` to check vector 0 and vector 1.
- Step 3: Inspect the `.map` file for `.data` LMA vs VMA addresses.
